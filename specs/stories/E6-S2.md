# E6-S2 — Endorsement service: atomic, immutable

- **ID:** E6-S2
- **Epic:** E6 — Endorsements
- **Layer:** Service
- **Group:** S3-C
- **Sprint:** 3
- **Depends on:** E6-S1, E5-S2
- **Traces:** AC-06, AC-10, NFR-02

## Description

Implement `src/service/endorsement_service.py`: in a single database transaction it validates the request with
the E6-S1 rules, appends an immutable `Endorsement` row (table `endorsements`: policy id, type, before/after
values, premium delta, actor, created_at), updates the `Policy` projection's attributes, moves the status to
`ENDORSED` via the state machine and appends a `PolicyStateTransition`. Any failure rolls everything back.

## Acceptance Criteria

1. [AC-06] A `CHANGE_ADDRESS` on `MO-2026-000001` (status `ACTIVE`) from `1 Sample Street, Testville` to `2 Sample Road, Testville` creates one `Endorsement` linked to that policy with `before`/`after` JSON holding both addresses and `premium_delta = Decimal("0.00")`, updates the policy address, and sets status `ENDORSED` _(category: functional)_
   - Verify: call `endorse(policy_number, CHANGE_ADDRESS, payload, actor_id)`; assert one endorsement row with the listed values and `policy_id` of the policy; reload the policy and assert the new address and status `ENDORSED`
2. [AC-06] A `CHANGE_SUM_INSURED` on `MO-2026-000001` from `500000.00` to `600000.00` updates `policies.sum_insured` to `600000.00` and `policies.premium` to the recomputed annual premium (`18600.00` = 600000.00 × 0.0310 on MOTOR v1), and the endorsement row stores the E6-S1 `premium_delta` quantized to 0.01 _(category: functional)_
   - Verify: endorse with the new sum insured; assert the policy's `sum_insured == Decimal("600000.00")` and `premium` equals the calculator result for the policy's rule version; assert `endorsement.premium_delta` equals `premium_delta(...)` from E6-S1
3. [AC-06] Atomicity: if any step fails after the endorsement insert (e.g. the transition repository `add` raises), no endorsement row, no policy attribute change and no transition row persist, and the API maps the failure to HTTP 500 `INTERNAL_ERROR` _(category: integration)_
   - Verify: patch `PolicyStateTransitionRepository.add` to raise; call `endorse` and assert the exception propagates; assert `endorsements` and `policy_state_transitions` counts unchanged and the policy's address, sum insured, premium and status equal their prior values; assert the API response is 500 with `error.code` `INTERNAL_ERROR`
4. [AC-10] Endorsing a policy in `LAPSED`, `CANCELLED` or `RENEWED` raises `InvalidPolicyStateException` (API 409 `INVALID_POLICY_STATE`) and writes nothing; a second endorsement on an `ENDORSED` policy succeeds and appends a transition `ENDORSED → ENDORSED` _(category: functional)_
   - Verify: endorse a CANCELLED policy and assert `InvalidPolicyStateException` with no new rows; endorse an ENDORSED policy and assert success, 2 endorsement rows total and a transition row with `from_status = ENDORSED`, `to_status = ENDORSED`
5. [—] `EndorsementRepository` exposes only `add(...)` and reads; endorsements are never updated or deleted, so after 3 endorsements the history returns 3 rows with their original `before`/`after` values unchanged _(category: security)_
   - Verify: assert the repository has no attribute containing `update` or `delete`; perform 3 endorsements and assert the first row's `after` value is unchanged after the third; run `backend/tests/architecture/` and assert it passes
