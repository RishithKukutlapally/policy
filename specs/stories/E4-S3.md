# E4-S3 — Manual review queue: underwriter approve/decline, audited

- **ID:** E4-S3
- **Epic:** E4 — Application & underwriting
- **Layer:** Service
- **Group:** S2-D
- **Sprint:** 2
- **Depends on:** E4-S2, E1-S3
- **Traces:** AC-14, NFR-02, NFR-04

## Description

`src/service/underwriting_service.py` gives underwriters a queue of `MANUAL_REVIEW` applications and lets them
approve (→ `AUTO_BIND`) or decline (→ `DECLINED`) with reason codes from the rule version the case was decided
on. Each decision appends an `underwriting_decisions` row and an `audit_records` row carrying the actor id.
Router `src/api/routers/underwriting.py` exposes `GET /api/underwriting/queue`,
`POST /api/underwriting/applications/{application_id}/decision` (body `{decision: APPROVE|DECLINE, reason_codes,
comment}`) and `GET /api/underwriting/applications/{application_id}/audit` for `UNDERWRITER`.

## Acceptance Criteria

1. [AC-14] `GET /api/underwriting/queue` as UNDERWRITER returns 200 with only `MANUAL_REVIEW` applications, oldest `created_at` first, each with `application_id`, `product`, masked applicant, `reason_codes` and `rule_version` _(category: integration)_
   - Verify: seed one AUTO_BIND, one DECLINED and two MANUAL_REVIEW applications; GET the queue as `uw-001`; assert exactly the two MANUAL_REVIEW ids in creation order and no raw Aadhaar/PAN in the body
2. [AC-14] `POST .../decision` with `{decision: "APPROVE", reason_codes: ["MO-UW-900"], comment: "Vehicle inspected"}` as `uw-001` returns 200, sets the application to `AUTO_BIND`, and appends an `underwriting_decisions` row `{decision: "AUTO_BIND", decided_by: "uw-001", reason_codes: ["MO-UW-900"]}` _(category: functional)_
   - Verify: create a MANUAL_REVIEW MOTOR application; POST the APPROVE decision; assert 200 and status; assert the decision table now has 2 rows for the application (SYSTEM + uw-001)
3. [AC-14] `POST .../decision` with `{decision: "DECLINE", reason_codes: ["MO-UW-902"]}` sets status `DECLINED`; a reason code not in that rule version's `reason_codes` (e.g. `TL-UW-001` on a MOTOR case) or an empty list returns 422 `VALIDATION_ERROR`; deciding an application not in `MANUAL_REVIEW` returns 409 `INVALID_APPLICATION_STATE` _(category: functional)_
   - Verify: POST DECLINE and assert status `DECLINED`; POST APPROVE on another case with `["TL-UW-001"]` and with `[]` and assert 422; POST APPROVE on an AUTO_BIND application and assert 409 `INVALID_APPLICATION_STATE`
4. [AC-14] Every approve/decline writes one `audit_records` row with `actor_id: "uw-001"`, `actor_role: "UNDERWRITER"`, `action` `UW_APPROVE` or `UW_DECLINE`, `entity_type: "APPLICATION"`, the `application_id` and the request `X-Correlation-ID` _(category: security)_
   - Verify: POST an APPROVE decision with `X-Correlation-ID: corr-uw-1`; query `audit_records` for the application; assert exactly one row with those values
5. [AC-14] Queue and decision endpoints return 401 `UNAUTHENTICATED` without actor headers and 403 `FORBIDDEN` for `CUSTOMER`; the queue GET is also allowed for `ADMIN` _(category: security)_
   - Verify: call the queue and decision endpoints with no headers (401) and as CUSTOMER (403); GET the queue as ADMIN and assert 200
