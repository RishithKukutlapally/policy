# E7-S3 — End-of-day job: renew + lapse, idempotent

- **ID:** E7-S3
- **Epic:** E7 — Renewal, lapse & payments
- **Layer:** Service
- **Group:** S4-C
- **Sprint:** 4
- **Depends on:** E7-S1, E7-S2
- **Traces:** AC-07, AC-18, NFR-02

## Description

Implement `src/service/end_of_day_service.py` with `run_end_of_day(as_of, actor_id)`. For every `ACTIVE` or
`ENDORSED` policy it applies the E7-S1 decision: `RENEW` moves the policy to `RENEWED` and issues a new-term
policy in `ACTIVE` with the refreshed premium; `LAPSE` moves it to `LAPSED`. Each policy is processed in its
own transaction; a failure is logged (no PII) and skipped, and re-running the same date changes nothing.

## Acceptance Criteria

1. [AC-07] With `as_of = 2027-01-15`, a paid policy `MO-2026-000001` (expiry `2027-01-14`) becomes `RENEWED` and a new policy is issued with a new number (e.g. `MO-2027-000001`), `previous_policy_number` = the old policy number, status `ACTIVE`, term `2027-01-15`–`2028-01-14`, and the refreshed premium and rule version from the active MOTOR version _(category: functional)_
   - Verify: seed the policy and a full payment; call `run_end_of_day(date(2027, 1, 15), actor_id)`; assert old status `RENEWED`, a new policy with the listed fields, and 2 new transition rows (`ACTIVE → RENEWED` for the old, `NULL → ACTIVE` for the new)
2. [AC-07] With `as_of = 2027-02-15`, an unpaid policy with expiry `2027-01-14` (grace end `2027-02-14`) becomes `LAPSED` with a transition row; with `as_of = 2027-02-14` it is untouched (still in grace) _(category: functional)_
   - Verify: run for `2027-02-14` and assert status unchanged and no transition row; run for `2027-02-15` and assert status `LAPSED` and one `ACTIVE → LAPSED` transition row
3. [AC-18] `run_end_of_day` is reachable from both DEC-011 entry points — `POST /api/admin/end-of-day` (actor = admin) and `python -m src.jobs.end_of_day --as-of YYYY-MM-DD` (actor `system-eod`) — and re-running for the same `as_of` through either renews and lapses nothing twice: the second run returns `{renewed: 0, lapsed: 0}` and `policies` / `policy_state_transitions` row counts are identical to after the first run _(category: functional)_
   - Verify: seed 3 due-and-paid and 2 past-grace-unpaid policies; run once and assert `{renewed: 3, lapsed: 2}`; run `python -m src.jobs.end_of_day --as-of <same date>` and assert exit 0 with `{renewed: 0, lapsed: 0}` and unchanged row counts
4. [AC-18] If processing one policy raises, that policy's transaction rolls back, the error is logged as a JSON line with the policy number and correlation id (no Aadhaar/PAN), the remaining policies are processed, and a later re-run completes the skipped policy exactly once _(category: integration)_
   - Verify: patch the calculator to raise for one of 3 due policies; run and assert the other 2 are renewed and the result lists 1 failure; capture logs and assert no 12-digit Aadhaar or PAN pattern; remove the patch, re-run and assert exactly 1 more renewal
5. [—] The job only appends `PolicyStateTransition` rows and inserts new-term policies; it never deletes or rewrites existing transitions, payments or endorsements _(category: security)_
   - Verify: snapshot all rows of `policy_state_transitions`, `premium_payments` and `endorsements` before the run; run the job; assert every pre-existing row is present and byte-identical afterwards
