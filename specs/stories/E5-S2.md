# E5-S2 — Policy issuance service + transition log

- **ID:** E5-S2
- **Epic:** E5 — Policy issuance & lifecycle
- **Layer:** Service
- **Group:** S3-B
- **Sprint:** 3
- **Depends on:** E5-S1, E4-S2
- **Traces:** AC-05, NFR-02

## Description

Implement `src/service/policy_issuance_service.py`, which turns an `Application` in status `AUTO_BIND` into a
`Policy` (table `policies`) with a unique policy number, effective date, expiry date, sum insured and the
quoted premium, in status `ACTIVE`. Every status change is recorded as an append-only
`PolicyStateTransition` row (table `policy_state_transitions`), and the application moves to `ISSUED` in the
same transaction.

## Acceptance Criteria

1. [AC-05] Issuing an `AUTO_BIND` MOTOR application with sum insured `500000.00` (vehicle_age_years 2, engine_cc 998, zone `B`, ncb_percent `"0"`) and quoted premium `15500.00` (= 500000.00 × 0.0310, E2-S1 v1) on `2026-03-01` creates a `Policy` with status `ACTIVE`, `effective_date = 2026-03-01`, `expiry_date = 2027-02-28` (12-month term from the rule set), `sum_insured = Decimal("500000.00")`, `premium = Decimal("15500.00")` and the quote's `rule_version` _(category: functional)_
   - Verify: seed an AUTO_BIND application from a persisted MOTOR quote; call `issue(application_id, actor_id, as_of=date(2026, 3, 1))`; assert every listed field on the returned `Policy` and that `premium` is a `Decimal` with exponent `-2`
2. [AC-05] Policy numbers follow `<PRODUCT_PREFIX>-<YYYY>-<6-digit sequence>` (`TL`, `MO`, `HH`) and are unique: the first MOTOR policy of 2026 is `MO-2026-000001`, the next is `MO-2026-000002`, and a UNIQUE constraint on `policies.policy_number` rejects duplicates _(category: functional)_
   - Verify: issue two MOTOR and one HOUSEHOLD application in 2026; assert numbers `MO-2026-000001`, `MO-2026-000002`, `HH-2026-000001`; assert every number matches regex `^(TL|MO|HH)-\d{4}-\d{6}$`; attempt a raw insert of a duplicate number and assert `IntegrityError`
3. [AC-05] Issuing an application whose status is not `AUTO_BIND` (e.g. `MANUAL_REVIEW`, `DECLINED`, or already `ISSUED`) raises `InvalidApplicationStateError` (API 409 `INVALID_APPLICATION_STATE`) and creates no `Policy` and no `PolicyStateTransition` row _(category: functional)_
   - Verify: call `issue` for applications in `MANUAL_REVIEW`, `DECLINED` and `ISSUED`; assert the error is raised each time; assert `policies` and `policy_state_transitions` row counts are unchanged
4. [AC-05] Issuance writes one `PolicyStateTransition` (`from_status = NULL`, `to_status = ACTIVE`, `actor_id`, `occurred_at`), one first-term `PremiumPayment` (`due_date = effective_date`, `amount = premium` — first term paid at issuance) and sets the application status to `ISSUED` in the same transaction; a failure after the policy insert leaves no policy, no transition and the application still `AUTO_BIND` _(category: integration)_
   - Verify: issue an application and assert exactly one transition row, one `premium_payments` row of `15500.00` and application status `ISSUED`; inject an exception into the transition repository `add`; assert the policy row is absent and the application status is still `AUTO_BIND`
5. [—] `PolicyStateTransitionRepository` exposes only `add(...)` and read methods; there is no update or delete method and any `UPDATE`/`DELETE` of `policy_state_transitions` is rejected by the architecture test / hook `append-only-repository-check` _(category: security)_
   - Verify: assert via `dir()` that the repository has no attribute containing `update` or `delete`; run `backend/tests/architecture/` and assert it passes; run the `append-only-repository-check` hook self-test and assert it blocks a sample `session.delete(transition)`
