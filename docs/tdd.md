# TDD Discipline — PolicyForge

Every line of production code in this repository was generated by a Claude Code agent, and every agent
worked test-first. This document records the discipline, how it is enforced, and one worked example end
to end.

## 1. The rule

> **No production code is written until a test that requires it exists and fails.**

Stated in `CLAUDE.md` ("TDD mandatory: test first, then implement") and in `.claude/program.md`
("Write failing tests FIRST… Tests define the contract; code fulfils it"). Every implementation prompt
given to a generator agent repeats it and demands evidence:

> *write the test file FIRST, run pytest, paste the failing output in your report, then implement until green.*

## 2. The cycle we actually run

| Phase | What happens | Evidence |
|-------|--------------|----------|
| 🔴 **Red** | The agent writes the test file and runs the suite. It fails — usually `ModuleNotFoundError`, or an assertion on a value nothing produces yet. | The failing output is quoted in the agent's hand-back report and reproduced in this document. |
| 🟢 **Green** | The agent writes the smallest implementation that satisfies the test, then re-runs the suite until it passes. | `pytest -q` summary in the report; CI re-runs it. |
| 🔵 **Refactor** | Length, typing, lint and layering gates force the design to stay clean: functions < 50 lines, files < 300 lines, `mypy --strict`, `ruff`, and five import-linter contracts. Behaviour must not change — the tests stay green. | e.g. `src/repository/models.py` (314 lines) was split into a package with **477 tests before and 477 after**, zero schema changes. |

Commits follow the same order, so the history shows it. `docs/commit-plan.md` lists, per story, the
`test:` commit that must precede the `feat:` commit.

## 3. How the red phase is guaranteed, not just promised

An agent could claim it wrote tests first. Three things make that hard to fake:

1. **The failing output is demanded in the hand-back** and is quoted below verbatim.
2. **Structural tests were proven against deliberately broken fixtures.** For `backend/tests/architecture/`
   the agent planted real violations — a repository `delete` method, a `float` premium, a `date.today()`
   outside `src/lib/clock.py`, an `api → repository` import, an `op.drop_table` migration, a second
   Alembic head — confirmed each test caught them, then deleted the fixtures and confirmed green again.
3. **Guard hooks block the wrong code at write time**, so a test-less shortcut is stopped before it lands
   (`premium-precision-check`, `policy-immutability-check`, `pii-redaction-check`,
   `append-only-repository-check`, `shell-immutability-check`; 58-case self-test in CI).

Where an agent deviated, it is recorded rather than hidden: two Sprint-2 domain agents wrote code before
tests. Their tests pass, but the red phase was not observed — noted here and in the knowledge deposits so
the instruction could be tightened, which it was for every agent afterwards.

## 4. Worked example — AC-04, the underwriting reason-code matrix

**The criterion.** *Underwriting decision returns AUTO_BIND / MANUAL_REVIEW / DECLINE with reason codes
referenced from the active policy version.*

### 🔴 Red — the test comes first

`backend/tests/ac/test_ac04_underwriting_decision.py` was written against the **real** v1 rule files, with
no implementation in existence:

```python
@pytest.mark.ac("AC-04")
@pytest.mark.parametrize(
    ("vehicle_age_years", "sum_insured", "expected_decision", "expected_codes"),
    [
        (3,  Decimal("500000"),  Decimal, ()),                       # clean risk  -> AUTO_BIND
        (12, Decimal("500000"),  "MANUAL_REVIEW", ("MO-UW-002",)),   # ageing vehicle
        (16, Decimal("500000"),  "DECLINE",       ("MO-UW-001",)),   # too old
        (16, Decimal("3000000"), "DECLINE",       ("MO-UW-001", "MO-UW-002", "MO-UW-003")),
    ],
)
def test_ac04_motor_decision_matrix(...):
    """AC-04: decision and reason codes come from the active rule version."""
```

First run:

```
ERROR tests/ac/test_ac04_underwriting_decision.py
ModuleNotFoundError: No module named 'src.domain.underwriting_rules'
Interrupted: 2 errors during collection
```

The test cannot pass by accident: the expected reason codes are read from
`backend/policy_rules/motor/v1.json`, so a hard-coded decision table would fail the moment the rule file
changed.

### 🟢 Green — the smallest thing that satisfies it

`src/domain/underwriting_rules.py` evaluates `underwriting.rules[]` in file order through the pure
`condition` evaluator, collects every matching `reason_code`, and returns the **most severe** match:

```
DECLINE > MANUAL_REVIEW > AUTO_BIND
```

with the codes sorted ascending and the `rule_version` recorded. Nothing matches → `AUTO_BIND` with no
codes. A rule naming a code absent from `underwriting.reason_codes` raises rather than inventing one.

The derived matrix (from the v1 files, not from prose):

| Product | Condition | Decision | Reason code |
|---------|-----------|----------|-------------|
| MOTOR | `vehicle_age_years > 15` | DECLINE | `MO-UW-001` |
| MOTOR | `vehicle_age_years > 10` | MANUAL_REVIEW | `MO-UW-002` |
| MOTOR | `sum_insured > 2500000` | MANUAL_REVIEW | `MO-UW-003` |
| TERM_LIFE | `age + term_years > 75` | DECLINE | `TL-UW-001` |
| TERM_LIFE | `sum_insured > 10000000` | MANUAL_REVIEW | `TL-UW-002` |
| TERM_LIFE | `has_pre_existing_condition == true` | MANUAL_REVIEW | `TL-UW-003` |
| HOUSEHOLD | `construction_type == THATCH` | DECLINE | `HH-UW-001` |
| HOUSEHOLD | `in_flood_zone and sum_insured > 5000000` | MANUAL_REVIEW | `HH-UW-002` |

### 🔵 Refactor — with the tests holding the behaviour

The severity comparison moved into a small ordering helper, condition evaluation stayed in
`src/domain/condition.py`, and the module stayed pure: imports limited to `src.types` and the standard
library, enforced by an import-linter contract. The tests never changed.

### The criterion then travelled outward

The same AC id follows the behaviour up the layers, so a regression anywhere fails a test that names AC-04:

| Layer | Test |
|-------|------|
| Domain | `tests/ac/test_ac04_underwriting_decision.py` |
| Service + API | `tests/ac/test_ac04_decision_api.py` |
| Underwriter workflow | `tests/ac/test_ac14_underwriter_decision.py` |
| Admin override | `tests/ac/test_ac09_admin_override.py` |
| Browser | Playwright spec with `AC-04` in its title |

## 5. Second example — NFR-01, where red mattered most

The endorsement agent verified that quantizing at each step instead of once at the end changes the answer:

| Approach | Result |
|----------|--------|
| Round every intermediate (`3100/365 → 8.49`, then `× 183`) | `1553.67` ❌ |
| Quantize once at the end (`3100 × 183 / 365`) | **`1554.25`** ✅ |

A 58-paisa error that no amount of code review reliably catches, and that a test written first does.

## 6. Traceability

- Every acceptance criterion `AC-NN` has at least one test named `test_acNN_*` carrying
  `@pytest.mark.ac("AC-NN")`; Playwright specs put the id in the test title.
- `/ac-coverage` builds the authoritative matrix into `specs/reviews/ac-coverage.md` and fails when any
  criterion has no test.
- `scripts/ac_audit_agent.py` adds a second opinion: a read-only Claude agent judges whether the tests
  genuinely exercise each criterion rather than merely mentioning it.
